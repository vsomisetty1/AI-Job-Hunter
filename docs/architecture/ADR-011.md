# ADR-011: Rule-based filtering and scoring, with optional Claude on a shortlist

**Status:** Accepted (Phase 6)

## Context
Discovery stores every valid posting from the tracked boards (about 1,700 from seven
boards in the Phase 5 validation). The user needs the few that fit, ranked, with reasons
they can check. Scoring must cost nothing by default (ADR-006), stay current when jobs,
the profile or the preferences change, and must not burn API spend when Claude is on.

## Decision
- **One pipeline:** Discovery → Deduplication → Filtering → Scoring
  (`services/pipeline_service.py`). Scheduled and manual discovery runs execute the whole
  pipeline; settings and profile changes run the last three stages (`rescore`). A lock
  serialises runs (single process, ADR-005). Each stage is an `agent_runs` row.
- **Filter decisions live on the job:** `filter_result` (every rule's outcome and reason),
  `filter_reason`, `filter_hash`, `filtered_at`; rejected jobs move to `filtered`, and
  back to `new` when they pass again. User decisions (`shortlisted`, `skipped`, `applied`)
  and `expired` are never touched. Missing data never rejects a job.
- **Cross-board duplicates are links, not deletions:** `jobs.duplicate_of` points at the
  earliest open posting with the same fingerprint at another company row; the filter's
  `duplicate` rule drops the copy, and an expired original releases it.
- **Scores are current-state rows:** one `job_scores` row per job + profile +
  `scoring_method` (`rules` | `claude`), updated in place (migration 0004 added
  `updated_at` and made the table mutable). Claude-only columns are nullable; CHECKs keep
  Claude rows attributable (model, prompt version) and rule rows token-free.
- **Input hashes make reruns cheap and correctness explicit:** the filter and the rule
  scorer hash their version plus every input they read and skip unchanged jobs. A Claude
  row stores the rule row's hash it was computed from; it is the job's *effective* score
  only while that hash still matches, otherwise the rule score is used and the job is
  queued for Claude again.
- **Claude only for a shortlist, bounded three ways:** rule score ≥ the user's minimum,
  best first; per-run and rolling 24-hour caps on real calls (counted from
  `agent_runs.output_summary.claude.calls`, so restarts do not reset them); client-side
  pacing (`llm/rate_limit.py`) that cache hits bypass. Any Claude failure leaves rule
  scores intact. The job posting is sent as untrusted data and the candidate summary has
  no name, contact details or links.

## Consequences
- Every number on the Jobs page can be explained from stored data, without Claude.
- Changing preferences rewrites every open job's filter row and score once (thousands of
  rows, in pages of 500, one short transaction each).
- Rule-based skill matching only knows the built-in skill taxonomy plus the candidate's
  own listed skills; Claude (or the planned Claude Code command path) covers synonyms.
- The daily cap counts calls recorded by finished scoring stages; calls made outside the
  pipeline would not be counted (none exist today).
