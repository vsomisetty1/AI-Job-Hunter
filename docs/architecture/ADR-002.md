# ADR-002: PostgreSQL as the only datastore; frozen SQL migrations

**Status:** Accepted (Phase 2; extended by migrations 0002 and 0003)

## Context
The app needs relational data (profiles, resumes, jobs, applications), JSON payloads (raw
job data, parsed resumes, run details), uniqueness guarantees (one running discovery run,
unique job URLs) and a cache. Running Redis, a queue or a document store next to it would
mean more moving parts on a personal machine.

## Decision
- PostgreSQL 15+ is the single store (CI uses 19). JSONB holds semi-structured data, and
  partial unique indexes enforce invariants (e.g. `uq_discovery_runs_one_running`). The
  LLM cache is a table (`llm_cache_entries`).
- The schema is hand-written SQL. `backend/schema.sql` is the readable reference at head.
- Each Alembic revision executes a **frozen** SQL file in `migrations/sql/`, pinned by
  SHA-256 in `tests/unit/test_schema_sql.py`. Applied migrations are never edited.
- Conventions:
  - uuid keys
  - `timestamptz`
  - enum-like columns as `text` + CHECK (cheap to evolve)
  - named constraints (`ck_`, `uq_`, `fk_`, `ix_`, `trg_`)
  - `updated_at` triggers
  - deleting a job is blocked while applications exist
- SQLAlchemy models mirror the schema; they do not generate it.

## Consequences
- The database enforces invariants itself (CHECKs, FKs, partial indexes), so bugs in
  application code cannot corrupt state silently.
- `tests/sql/validate_catalog.sql` and `behavior.sql` compare the migrated catalog with
  `schema.sql` and exercise constraints. Migration tests run upgrade and downgrade on real
  Postgres.
- A schema change touches several files: the SQL file, the revision, `schema.sql`, the
  model, the hash pin and the SQL tests. That is deliberate friction.
- Tables for later phases (`job_scores`, `applications`, ...) already exist unused, so
  later migrations should alter them rather than re-create them.
