# ADR-013: Data lifecycle and storage cleanup

**Status:** Accepted (MVP validation, before browser automation)

## Context
MVP validation generated about 40 packages for one resume and found 166 stored files
(about 4 MB) after a few regenerations. Nothing was ever deleted: superseded packages kept
their tailored resume and cover letter files, deleting a resume left the rendered PDF/DOCX
of every version behind, and there was no way to delete a package at all. A failed request
between "file written" and "row committed" also leaves a file that no row points to.

## Decision
- **Kept until the user deletes them:** uploaded resumes and every parsed and tailored
  version; live (generated, reviewed), approved and submitted packages and everything they
  point to. Deleting a resume deletes its original file and the renders of all its versions.
- **Retention:** superseded, rejected and failed packages are deleted after
  `PACKAGE_RETENTION_DAYS` (default 90, measured from `updated_at`), together with the tailored
  resume version and cover letter they created, unless an application or another package
  still points to them.
- **Manual delete:** `DELETE /packages/{id}` for superseded, rejected, failed, generated or
  reviewed packages. Approved and submitted ones return 409: reject an approved one first;
  a submitted one is a record of something that happened.
- **Orphan sweep:** files under `resumes/` and `generated/` that no row references are deleted
  once older than `ORPHAN_GRACE_HOURS` (default 24). The grace period exists because generation
  writes files just before the transaction that references them commits.
- **Order:** rows first, files after commit. A failed file delete is logged and left for the
  sweep; a file is never deleted while a row may still point to it.
- **Where it runs:** the daily maintenance job (`LifecycleService.run`), plus
  `POST /system/storage/cleanup` on demand. `GET /system/storage` reports usage per area,
  orphans, package counts by status and what the next prune would remove.
- `StorageBackend.list_files(prefix)` was added to both backends (local and Supabase) so the
  sweep works on either.

## Consequences
- Superseded versions stay available for 90 days for comparison, then go; anything an
  application used is never pruned.
- The sweep must list every stored file and every referenced path: fine for a personal
  install (thousands of files), not for a very large store.
- An orphan younger than the grace period survives one extra day.
