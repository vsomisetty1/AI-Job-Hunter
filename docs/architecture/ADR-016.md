# ADR-016: Hardening for release: local request guard, approval mode only, API contract, containers, backups

**Status:** Accepted (Phase 10). Amends ADR-004 (security), ADR-010 (testing), ADR-014
(approval mode, now also enforced for settings and applications).

## Context
A review before release found that the local-only design (ADR-004) relied on the server
listening on 127.0.0.1 and nothing else, and listed these risks:
- **DNS rebinding:** a web page on another site can re-point its own name at 127.0.0.1;
  the browser then lets it read the API's answers (resumes, profile), because the server
  answered any `Host`.
- **Cross-site writes (CSRF):** any page open in the browser can send "simple" POSTs
  (forms, multipart uploads) to localhost without a CORS preflight.
- **Autonomous mode could be switched on but did nothing:** `PATCH /settings` accepted
  `application_mode=AUTONOMOUS_MODE` with a threshold and a daily cap, and the database
  allowed it, although no code path submits without the user (ADR-014).
- **No backup:** months of outcomes lived in one Docker volume and one folder.
- **Frontend types were copied by hand** from the backend and tested only against mocked
  fetch, so an API change could break pages silently.
- **No container story:** the Dockerfiles were placeholders.

## Decision
- **Local request guard** (`core/middleware.LocalRequestGuardMiddleware`), before every route:
  - `Host` must be in `ALLOWED_HOSTS` (default `localhost, 127.0.0.1, ::1`; port ignored).
    Anything else gets 400 `host_not_allowed`. `*` is refused unless `AUTH_MODE=api_key`.
  - A state-changing request (not GET/HEAD/OPTIONS) that carries `Origin` must come from
    `CORS_ORIGINS` or from the API's own origin (Swagger UI); `Origin: null` and
    `Sec-Fetch-Site: cross-site` without an allowed origin get 403 `cross_site_request`.
    Requests with neither header (curl, scripts) pass: browsers always send `Origin` on a
    cross-origin POST.
  - Every response carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
    `Content-Security-Policy: frame-ancestors 'none'` and `Referrer-Policy: no-referrer`
    (the frontend sends the same), so the review-and-submit screen cannot be framed.
- **Approval mode only, in the API and the database:** the settings API rejects
  `application_mode`, `auto_apply_threshold` and `daily_application_cap` with a 422 that says
  why, and no longer returns the two numbers. Migration 0008 resets any stored
  `AUTONOMOUS_MODE` and limits `settings.application_mode` and `applications.application_mode`
  to `APPROVAL_MODE`, like `application_submissions.mode` (0006). The two numeric columns stay,
  unused, for a future decision. **Autonomous mode needs a new ADR that supersedes this
  rule and ADR-014's, and a migration that relaxes these constraints.**
- **API contract:** `scripts/gen_api_contract.py` turns the backend's OpenAPI spec into
  `frontend/src/types/api.gen.ts` (response shapes with every field the backend sends,
  request shapes with `Input` suffix, and the list of operations). Three checks use it:
  - backend `tests/unit/test_api_contract.py`: the committed file matches the code;
  - frontend `src/types/contract.ts` (typecheck): every hand-written response type accepts
    what the backend sends and expects no field it does not send; request bodies send no
    field the backend rejects;
  - frontend `src/types/contract.test.ts`: every function in `src/lib/api` calls an
    operation (method and path) the backend serves.
  Backend schemas say what they mean (`Literal` values for statuses and sources, typed
  models for discovery run details, answer evidence and editable fields) so the contract
  can check them.
- **Containers for personal use:** a backend image (Python 3.14 slim, Chromium headless
  shell, non-root user, migrations on start, health check) and a frontend image (Next.js
  standalone, non-root, read-only filesystem). `docker-compose.yml` runs db, backend and
  frontend and publishes every port on 127.0.0.1 only. The backend binds 0.0.0.0 inside its
  container, which `AUTH_MODE=none` allows only with `CONTAINER_LOOPBACK_ONLY=true` (set by
  the image); the Host allowlist still refuses other names.
- **Backups:** `scripts/backup.sh` / `scripts/restore.sh` (BACKUP_AND_RECOVERY.md): a
  `pg_dump` custom-format dump plus a tarball of the stored files, a manifest with the
  schema revision and checksums; restore verifies checksums, refuses a newer schema and a
  running backend, and backs up the current state first.
- **Release hygiene:** one version (0.10.0) in `backend/pyproject.toml`, `Settings.app_version`
  and `frontend/package.json`, kept equal by a test; no placeholder files (a test fails on
  any `PLACEHOLDER - implemented in PHASE N`); oversized services split
  (`package_generator`/`package_workflow`/`package_inputs`;
  `automation_service`/`automation_facts`/`automation_recorder`/`automation_views`).

## Consequences
- Opening the app at a LAN address or a custom host name fails with 400 until that name is
  added to `ALLOWED_HOSTS` (and anything beyond loopback still needs `AUTH_MODE=api_key`).
- A backend change to a response or request model needs `python scripts/gen_api_contract.py`;
  CI fails otherwise. Endpoints that still return untyped dictionaries (the analytics
  summaries) are outside the contract until they get response models.
- Headed Chromium (watching a run, solving a CAPTCHA) is not available in the container;
  run the backend natively for that (DEPLOYMENT.md).
- Backups are plain files holding personal data; keeping them safe (disk encryption,
  off-machine copy) is the owner's job.
- Testing follows ADR-010; frontend-through-backend browser tests move to Phase 12 (the
  Phase 10 note in ADR-010 is superseded by the roadmap in PROJECT_STATE.md).
