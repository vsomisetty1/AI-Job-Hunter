# ADR-012: Application packages are built from facts and approved by a person

**Status:** Accepted (Phase 7)

## Context
Before any browser automation applies to a job, the material it sends (resume, cover letter,
answers) must exist, be inspectable and be approved. Generated application material has an
obvious failure mode: invented skills, employers, metrics or eligibility. A false claim on an
application is worse than a weaker but true one.

## Decision
- **A package is a stored, versioned object** (`application_packages`) linking a tailored
  resume version, a cover letter, answers and the score snapshot. Statuses: generating →
  generated → reviewed → approved → submitted, ending in rejected, failed or superseded. One
  live package per job and profile (partial unique index); regenerating supersedes the old one,
  and every resume version and cover letter version is kept.
- **Deterministic first, Claude optional** (ADR-006): Agents 6, 8 and 9 produce a complete
  package with no API key: reorder, respell and compose from resume/profile/settings facts.
  Claude is used only when asked per package (`use_llm`) and only for wording.
- **A truthfulness guard checks all wording** (`app/agents/truthfulness.py`): generated text may
  not name a skill or a number that the candidate's material lacks (a reworded bullet may only
  reuse numbers from its own role); tailored resumes keep contact details, roles (employer,
  title, location, dates, order), education, certifications and the set of projects identical,
  and never gain bullets or skills. Claude output that fails is dropped and noted;
  deterministic output that failed would be a bug and raises.
- **Traceability:** every resume change stores section, item, field, before, after, reason and
  time; every answer stores the facts it used; letters store the facts they quote.
- **Unknowns are flagged, not filled:** answers that facts cannot support (no salary target,
  relocation not stated, work authorization not set, skills not on the resume) or that are
  personal (why this company) are `needs_review` with low confidence.
- **Approval is the handoff to automation:** approving creates or updates the job's
  `applications` row (`ready`, APPROVAL_MODE) with the package's artifacts and an event;
  rejecting or regenerating an approved package withdraws it (`drafted`). "Submitted" is only
  recorded when the user says they applied; the app submits nothing.
- **Rendering is ATS-first:** one column, real text, standard fonts and section names, plain
  "-" bullets in PDFs (the built-in fonts encode "•" in a way extractors misread).

## Consequences
- Rule-based letters and "why this company" answers read as templates; they are flagged for
  personalisation, and Claude (or a future Claude Code command) can improve them.
- The guard is lexical: it catches new skills from the taxonomy or the candidate's list and new
  numbers, not every possible overstatement (e.g. "led" for "helped"). Review stays mandatory.
- Generation is a background task; an interrupted one is marked failed at startup.
