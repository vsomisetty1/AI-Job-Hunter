# ADR-003: Async SQLAlchemy with short, explicit units of work

**Status:** Accepted (Phase 3; refined in Phases 4–5)

## Context
The API does I/O-bound work: database, Claude, job boards, storage. Long transactions
held open across network calls would block other work, hold locks, and make failures
roll back unrelated writes.

## Decision
- Use SQLAlchemy 2 in async mode (asyncpg) with a lazily created engine
  (`core/database.py`).
- **One request = one transaction:** `get_db` commits when the handler returns and rolls
  back on error.
- **Repositories never commit.** They add, flush and query only.
- **Background work opens its own short transactions** via `session_scope()` or the
  injected `async_sessionmaker`. It **never holds a transaction open during a Claude call
  or an HTTP fetch**. Examples:
  - Discovery fetches a board with no transaction open, then persists one company in one
    short transaction.
  - Resume processing commits between Claude calls.
- Bookkeeping writes (`agent_runs`, the LLM cache) use their own transactions, so they
  survive a failing caller.

## Consequences
- Concurrency is safe at personal scale with a small pool (`DB_POOL_SIZE=5`).
- Handlers that start background work must commit before handing off. The pattern:
  set the status, `await db.commit()`, then submit the task.
- Tests use two modes:
  - `db_app`: each test in a rolled-back outer transaction joined with SAVEPOINTs
  - `build_live_app`: the real pool, for flows with concurrent sessions (resume
    processing, discovery)
- Supabase's transaction pooler (port 6543) is detected, and prepared statements are
  disabled for it.
