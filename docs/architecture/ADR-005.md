# ADR-005: In-process scheduler and background tasks (one worker)

**Status:** Accepted (Phase 3; extended in Phases 4–5)

## Context
The app needs periodic jobs (discovery, maintenance) and work outside the request cycle
(resume processing, manual discovery runs). Celery or RQ with a broker, or a separate
worker container, would add infrastructure to a personal tool.

## Decision
- `scheduler/scheduler.SchedulerService` wraps APScheduler's `AsyncIOScheduler` and is
  started and stopped by the app lifespan. Jobs use `max_instances=1` and
  `coalesce=True`. Jobs are registered in `scheduler/tasks.py`:
  - discovery every `DISCOVERY_INTERVAL_MINUTES`, incremental
  - maintenance daily
- `scheduler/background.BackgroundTaskManager` runs async work with bounded concurrency,
  de-duplication by key, status tracking (`/api/v1/system/tasks/{id}`) and cancellation
  on shutdown.
- The backend **must run with exactly one worker**; `python -m app` enforces it.
- Startup recovery (`recover_interrupted_work`) marks profiles, `agent_runs` and
  `discovery_runs` left `pending`/`running` by a previous process as failed or cancelled.
- Discovery-specific guards:
  - The database allows at most one running discovery run (a partial unique index), so
    a manual run and a scheduled run cannot overlap.
  - Scheduled runs honour `settings.discovery_enabled` at run time.

## Consequences
- No broker or extra process is needed, and the scheduler state is visible through the
  API.
- Task state lives in memory: tasks are lost on restart (and then marked
  cancelled/failed), and the app cannot scale horizontally as is.
- A sleeping laptop just delays jobs; missed runs coalesce into one.
- Moving to a durable queue later is contained: callers use
  `BackgroundTaskManager.submit` and the services are already task-agnostic.
