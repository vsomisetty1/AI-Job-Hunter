# ADR-010: Testing and CI strategy

**Status:** Accepted (Phase 3; applied in every phase since). Extended by ADR-016 (API
contract checks, Compose smoke test, backup round trip); the e2e phase number below is
superseded by the roadmap in PROJECT_STATE.md (Phase 12).

## Context
The owner asked how they can know the app works. Tests that run only by hand, or a
"testing phase" at the end, give no such confidence. Mocks of the database hide real SQL
and constraint behaviour, and calling real third-party services in CI makes builds flaky
and leaks data.

## Decision
- **Each phase ships its tests and CI changes in the same commit as the feature.**
- **Real PostgreSQL in tests** (`TEST_DATABASE_URL`; Postgres 19 in CI). Two app
  fixtures, `db_app` (rolled-back transaction) and `build_live_app` (real pool, tables
  cleaned), cover the two concurrency modes. Migration tests run upgrade and downgrade.
- **External services are never called in CI:**
  - Claude: `tests/fakes.FakeAnthropic`
  - HTTP (Supabase, job boards): `respx`, with realistic fixtures in
    `tests/fixtures/boards/`
  - Opt-in live tests use the `live` marker, deselected by default. They run on demand
    and weekly in `.github/workflows/live-connectors.yml`.
- **Strictness:**
  - pytest turns warnings into errors
  - CI fails if any test is skipped (a misconfigured database cannot silently skip
    everything)
  - `mypy --strict`
  - ruff including bandit rules
  - `pip-audit` and `npm audit`
  - an architecture test (ADR-001)
  - a schema hash pin (ADR-002)
- **Smoke test** (`scripts/smoke_backend.sh`): CI migrates, starts the real server with
  `python -m app`, calls the main endpoints, uploads a resume and waits for the profile,
  and starts a discovery run.
- **Frontend:** typecheck, lint, Vitest with Testing Library (fetch mocked per route),
  `next build`.
- **Real-world validation:** `scripts/validate_discovery.sh` and `docs/VALIDATION.md` for
  checks only possible against live services.
- **Dependencies:** latest stable versions, pinned exactly. Holdbacks are documented with
  their reason in `docs/TESTING.md`.

## Consequences
- A green CI means the app starts, migrates and serves its main flows on a real
  database.
- Test suites take longer and need a Postgres instance locally.
- Browser e2e (Playwright) is not in CI yet (Phase 10). The live provider checks run
  weekly, not per push.
